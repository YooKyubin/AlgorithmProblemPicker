# Feature Specification: JUNGOL 문제 검색·추천 CLI

**Feature Branch**: `001-jungol-problem-picker`

**Created**: 2026-10-19

**Status**: Draft

**Input**: README의 주요 기능인 문제 필터링, 정렬, 무작위 추천, 브라우저 열기를 구현한다.
로컬 캐싱은 제외한다. 정올의 데이터 제공 및 URL 필터 지원 범위를 조사하고,
풀이 여부는 CLI에서 지정한 정올 사용자, 완료자 수는 중복 제출을 제외한 푼 사람 수로 정의한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 조건에 맞는 문제 조회 (Priority: P1)

사용자는 난이도·정답률·푼 사람 수·지정 사용자의 풀이 여부를 조합해 문제를 찾는다.

**Why this priority**: 필요한 문제를 정확히 찾는 것이 도구의 기본 가치다.

**Independent Test**: 알려진 문제 목록에서 조건을 지정해 결과가 모든 조건을 만족하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 경계값을 포함한 문제 목록, **When** 세 수치의 범위를 함께 지정하면,
   **Then** 각 범위의 양 끝을 포함해 모든 조건을 만족하는 문제만 표시한다.
2. **Given** 공개 풀이 이력을 확인할 수 있는 지정 사용자, **When** 푼 문제 또는 안 푼 문제를 선택하면,
   **Then** 해당 사용자의 정답 처리 여부를 기준으로 결과를 구분한다.
3. **Given** 결과가 여러 페이지에 존재하는 조건, **When** 목록을 조회하면,
   **Then** 현재 표시 개수 제한과 관계없이 전체 후보를 기준으로 조건을 적용한다.
4. **Given** 결과가 없거나 사용자 정보를 확인할 수 없는 조건, **When** 조회하면,
   **Then** 결과 없음과 조회 실패를 구분해 안내한다.

### User Story 2 - 중복 없는 무작위 추천 (Priority: P1)

사용자는 동일한 조회 조건으로 원하는 개수의 문제를 추천받는다.

**Why this priority**: 풀 문제를 고르는 수고를 줄이는 핵심 기능이다.

**Independent Test**: 조건에 맞는 후보가 12개인 상황에서 5개 추천을 요청해 개수·조건·중복을 확인한다.

**Acceptance Scenarios**:

1. **Given** 적격 후보가 요청 개수 이상이면, **When** N개를 추천받으면,
   **Then** 모든 페이지의 적격 후보가 선택 대상이며 서로 다른 문제 N개를 반환한다.
2. **Given** 적격 후보가 요청 개수보다 적으면, **When** 추천받으면,
   **Then** 가능한 후보 전부를 한 번씩 반환하고 요청 개수와 실제 개수를 안내한다.
3. **Given** 후보 조회가 도중에 실패하면, **When** 추천을 실행하면,
   **Then** 일부 페이지로 만든 결과를 전체 후보의 정상 추천처럼 제공하지 않는다.

### User Story 3 - 원하는 순서로 조회 (Priority: P2)

사용자는 검색 결과를 난이도순, 정답률순, 푼 사람 수순 또는 무작위순으로 확인한다.

**Why this priority**: 쉬운 문제부터 풀거나 많은 사람이 푼 문제를 선택할 수 있다.

**Independent Test**: 지표와 동점이 알려진 문제 목록으로 정렬 순서와 중복 여부를 확인한다.

**Acceptance Scenarios**:

1. **Given** 필터를 통과한 전체 후보, **When** 지표와 오름차순 또는 내림차순을 선택하면,
   **Then** 전체 후보를 정렬한 뒤 표시 개수를 제한하고, 동점은 문제 번호 오름차순으로 표시한다.
2. **Given** 필터를 통과한 후보, **When** 무작위순을 선택하면,
   **Then** 조건을 유지한 채 각 문제를 한 번씩만 포함하는 순서로 표시한다.

### User Story 4 - 선택한 문제 열기 (Priority: P2)

사용자는 조회·추천 결과에서 고른 문제를 기본 브라우저로 연다.

**Why this priority**: 문제를 찾은 뒤 바로 풀이를 시작할 수 있다.

**Independent Test**: 알려진 문제 번호를 선택해 열리는 문제와 출력된 링크가 일치하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 문제 번호와 링크가 표시된 결과, **When** 한 개 또는 여러 개를 명시적으로 선택하면,
   **Then** 선택한 문제만 각각 한 번씩 기본 브라우저로 연다.
2. **Given** 브라우저 실행 실패, **When** 열기를 요청하면,
   **Then** 실패를 알리고 직접 열 수 있는 문제 링크를 표시한다.

### Edge Cases

- 수치 범위의 하한이 상한보다 크거나, 정답률이 0~100 밖이거나,
  푼 사람 수가 음수거나, 요청 개수가 양의 정수가 아니면 입력 오류로 처리한다.
- 난이도 미정 문제는 난이도 범위 지정 시 제외한다. 범위가 없으면 포함하며,
  난이도순 정렬에서는 방향과 관계없이 마지막에 표시한다.
- 지표를 확인할 수 없는 문제는 해당 지표 조건을 만족한다고 간주하지 않는다.
  지표 필터가 없으면 포함하되 미확인으로 표시하고 해당 지표 정렬에서 마지막에 둔다.
- 제출이 없는 문제의 정답률은 정올에 수치가 표시되면 그 값을 사용하고,
  수치가 없으면 미확인으로 처리한다. 푼 사람 수와 정답 제출 수를 혼동하지 않는다.
- 공개 풀이 이력이 확인되지 않는 사용자를 미풀이로 간주하지 않는다.
- 페이지 경계에서 같은 문제를 다시 보더라도 결과에는 문제 번호당 한 번만 포함한다.
- 접속 실패·접근 제한·조회 중단은 빈 결과와 구분한다. 조회 중 취소할 수 있어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 도구는 JUNGOL의 공개 문제를 대상으로 CLI에서 조회·추천·열기를 제공해야 한다.
- **FR-002**: 난이도, 정답률(0~100%), 푼 사람 수의 최소·최대 조건을 각각 또는 함께
  지정할 수 있어야 하며, 생략한 경계는 제한하지 않고 지정한 경계는 포함해야 한다.
- **FR-003**: 풀이 조건은 전체·푼 문제·안 푼 문제를 지원해야 한다.
  푼 문제·안 푼 문제를 요청할 때는 기준 사용자를 지정해야 한다.
- **FR-004**: 풀이 여부는 지정 사용자의 정올 정답 처리 여부를 따라야 하며,
  오답 제출만 있거나 제출하지 않은 문제는 안 푼 문제에 포함해야 한다.
- **FR-005**: 완료자 수는 동일 사용자의 중복 정답 제출을 제외한 푼 사람 수여야 한다.
  정답률은 정올이 표시하는 지표를 따르며 푼 사람 수를 분자로 재계산하지 않아야 한다.
- **FR-006**: 목록은 문제 번호·제목·난이도·정답률·푼 사람 수·문제 링크를 제공해야 한다.
  풀이 조건 사용 시 기준 사용자와 적용된 풀이 조건도 표시해야 한다.
- **FR-007**: 난이도·정답률·푼 사람 수의 오름차순·내림차순과 무작위순을 지원해야 한다.
  생략 시 문제 번호 오름차순, 지표 동점 시 문제 번호 오름차순이어야 한다.
- **FR-008**: 조회와 추천은 동일한 필터 의미를 사용해야 한다.
  표시 개수 제한은 전체 후보의 필터링·정렬 이후에 적용해야 한다.
- **FR-009**: 추천은 전체 적격 후보에서 문제마다 동일한 선택 기회를 부여하여
  요청 개수만큼 중복 없이 선택해야 한다. 연속 실행 사이의 중복 방지는 범위에 포함하지 않는다.
- **FR-010**: 후보가 부족하면 존재하는 후보 전부와 부족 안내를 반환해야 한다.
  후보가 0개인 정상 조회는 오류와 구분해 표시해야 한다.
- **FR-011**: 조회·추천만 실행해도 브라우저가 자동으로 열리지는 않아야 한다.
  명시적으로 선택한 문제만 기본 브라우저로 열고 실패 시 링크를 안내해야 한다.
- **FR-012**: 잘못된 입력·사용자 미지정·사용자 조회 실패·지표 제공 실패·접근 제한을
  원인과 함께 안내하고, 조건을 몰래 생략하거나 다른 지표로 대체하지 않아야 한다.
- **FR-013**: 후보를 다 확인하기 전 실패·취소된 작업을 완전한 조회·정렬·추천 성공으로
  표시하지 않아야 하며, 입력 오류와 작업 실패는 실패 종료 상태로 구분 가능해야 한다.
- **FR-014**: 문제 목록을 실행 사이에 재사용하는 로컬 캐싱, 오프라인 조회,
  수동 풀이 기록 저장은 구현 범위에서 제외해야 한다. 실행 중 임시 처리는 허용한다.
- **FR-015**: 기능에 필요한 자동 데이터 접근 허용 여부와 지표 제공 범위를 확인해야 하며,
  내부 데이터 접근 경로의 존재만으로 외부 자동 사용이 허용된다고 가정하지 않아야 한다.
- **FR-016**: 조회 진행 중 진행 상태와 취소 방법을 안내해야 하며,
  문제별 지표는 각 조회 시점의 값임을 전제로 해야 한다.

### Key Entities *(include if feature involves data)*

- **문제**: 번호, 제목, 링크, 난이도 또는 미정, 정답률 또는 미확인, 푼 사람 수 또는 미확인.
- **검색 조건**: 수치 범위, 풀이 조건, 기준 사용자, 정렬 기준·방향, 표시 개수.
- **기준 사용자**: CLI에서 지정한 정올 사용자 식별자와 공개 풀이 이력의 확인 가능 상태.
- **조회 결과**: 중복 제거된 적격 문제, 적용 조건, 조회 완료 여부와 조회 시점.
- **추천 요청·결과**: 검색 조건, 요청 개수, 선택된 문제, 실제 반환 개수와 부족 안내.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 각 필터의 경계와 조합을 포함한 검증 사례에서 결과의 100%가 모든 지정 조건을 만족한다.
- **SC-002**: 지표별 양방향 정렬 결과는 전체 후보 기준 기대 순서와 100% 일치하며,
  표시 개수를 줄여도 전체 정렬의 앞부분과 동일하다.
- **SC-003**: 후보가 충분한 모든 추천 사례에서 요청 개수와 반환 개수가 일치하고 중복은 0개다.
  후보 부족·0개 사례에서는 실제 개수와 안내가 일치한다.
- **SC-004**: 두 번째 페이지 이후의 후보도 추천 대상에 포함되고, 무작위순 조회에는
  누락·중복이 없음을 확인한다. 추천 확률의 동일성 검증 방법은 계획 단계에서 정한다.
- **SC-005**: 사용자는 문서의 예시를 따라 조건 지정 → 추천 → 선택 문제 열기를
  코드 수정 없이 수행할 수 있고, 선택하지 않은 문제의 브라우저 열기는 0건이다.
- **SC-006**: 입력 오류, 사용자 확인 실패, 접근 제한, 조회 중단 사례의 100%에서
  원인을 표시하며, 정상적인 결과 없음과 구분된다.

## Assumptions

- 이번 사용자 요청에 따라 로컬 캐싱을 제외한다. 기존 헌장 III의 영구 캐시 원칙보다
  이번 기능에 대한 명시적 지시를 우선하며, 중복 없는 추천 원칙은 유지한다.
- 최초 범위는 개인 사용, JUNGOL 공개 문제, 온라인 실행이다.
  프로그래머스·플랫폼 통합·문제 제출·계정 로그인·비공개 문제는 포함하지 않는다.
- 풀이 기준은 사용자가 답변한 대로 CLI에서 지정한 공개 사용자이며,
  완료자 수는 정올의 푼 사람 수다. 사용자 식별자는 사용자가 매번 지정할 수 있다.
- 난이도는 정올의 티어 순서를 따른다. 퀴즈·강의 등은 별도 지원을 요구하지 않는다.
- 목록 표시 개수 기본값은 20개, 추천 기본값은 1개로 한다. 이는 전체 후보 범위를 줄이지 않는다.
- 로컬 캐싱 없이 전체 후보를 확인하면 조회 시간이 늘어날 수 있다.
  데이터 접근 허용 여부, 전체 후보 및 필요한 지표의 확보 가능성은 구현 전 확인할 외부 의존성이다.
- 같은 실행에서도 정올의 문제·통계가 바뀔 수 있어 전체 사이트의 한 시점 스냅샷 일치는 보장하지 않는다.
- 데이터 접근 방식과 URL 지원 범위의 조사 근거는 별도 [조사 기록](discovery.md)에 보관한다.
