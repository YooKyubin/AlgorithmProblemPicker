## ISSUE-001: 티어 미정·미확인 문제로 인한 수집 중단

- **상태**: 미수정
- **확인일**: 2026-10-20

### 발생 내용

다음 명령으로 추천을 실행한 뒤, 수집 650개 로그 이후 목록 수집이 중단됐다.

```powershell
uv run jpick recommend --min-tier 9 --max-tier 14 --min-solvers 1000 --status unsolved --user yookyubin --count 2
```

```text
조회 실패: 목록 티어 필터가 적용되지 않았습니다.
```

상세 조회와 추천 단계에는 도달하지 못했다.

### 확인된 동작

- 현재 코드는 티어 범위를 지정하면 범위 밖 티어뿐 아니라 **미정·미확인 티어**를 만나도 같은 오류로 전체 수집을 중단한다.
- 오류에 문제 번호와 읽은 티어가 없어, 실제 실패가 범위 밖·미정·미확인 중 어느 경우였는지는 아직 확인하지 못했다. 정올의 필터 미적용으로 원인을 단정할 수 없다.
- 관련 위치: `src/algorithm_problem_picker/jungol.py`의 `_collect` 티어 검증.

### 수정 방향

- 티어 범위가 지정된 경우, 기본적으로 목록 요청 URL에 `unrated=exclude`를 적용해 정올에서 미정 문제를 먼저 제외한다. 현재 구현도 이 매개변수를 사용하므로 추가 로드에서도 해당 조건이 유지·적용되는지 확인한다.
- 티어 범위가 지정된 경우, 정상적으로 식별된 미정·미확인 문제는 해당 조건의 후보에서 제외하고 수집을 계속한다.
- 범위 밖 티어 반환과 미정·미확인 값을 구분해 처리하고, 실제 필터 적용 이상이 의심될 때는 문제 번호·읽은 티어·요청 범위를 진단에 포함한다.
- DOM 구조 변경이나 티어 파싱 실패는 정상적인 미확인 값으로 바꾸지 않고 오류로 유지한다.

### 완료 조건

- 최초 목록과 추가 로드 모두에서 URL의 `unrated=exclude` 조건이 유지·적용된다.
- 미정·미확인 문제 때문에 정상 후보의 추천까지 중단되지 않는다.
- 추천 결과는 지정한 티어 범위를 모두 만족한다.
- 범위 밖 티어·미정·미확인·파싱 실패를 구분하는 최소 회귀 검증을 추가한다.

## ISSUE-002: solver 수집을 위한 문제별 상세 조회로 인한 지연

- **상태**: 수정 방향 합의, 미구현
- **확인일**: 2026-10-20

### 발생 내용

사용 목적은 조건에 맞는 문제를 필터링한 뒤 무작위로 선택하는 것이다. 현재는 solver(맞힌 사람 수)를 확보하려고 후보마다 상세 페이지를 방문하므로, 적은 수의 문제를 추천받아도 상세 조회 비용이 발생한다.

현재 처리 순서는 다음과 같다.

1. 조건에 맞는 전체 문제 목록을 수집한다.
2. 난이도·정답률 조건을 적용한다.
3. 남은 후보 전부의 상세 페이지에서 맞힌 사람 수를 읽는다.
4. 맞힌 사람 수 조건을 적용한 뒤 정렬·추천한다.

`--count`가 작거나 맞힌 사람 수 조건을 생략해도 3번을 수행한다. 관련 위치는 `service.py`의 `Picker._run`과 `jungol.py`의 `read_details`다. 이번 이슈는 상세 조회가 추가되는 구조에 관한 것이며, 구체적인 지연 시간은 아직 측정하지 않았다.

### 확인된 지표 차이

정올 목록 화면은 난이도·정답률과 함께 **정답 제출 수**를 제공한다. 기존 solver인 **맞힌 사람 수**와는 다른 지표다.

1006번 ‘로봇’의 공개 목록과 상세 화면을 비교한 관측값:

| 항목 | 값 | 확인 위치 |
| --- | --- | --- |
| 정답 제출 수 | 3,145 | 목록의 ‘정답’ 열 및 상세의 ‘정답 수’ |
| 전체 제출 수 | 12,977 | 목록의 ‘시도’ 열 및 상세의 ‘제출 수’ |
| 정답률 | 24.24% | 목록의 ‘정답률’ 열 |
| 맞힌 사람 수(solver) | 2,485 | 상세의 ‘맞힌 사람’ 통계 |

정답 제출 수에는 동일 사용자의 중복 정답 제출도 포함된다. 따라서 이번 변경은 같은 값을 다른 위치에서 읽는 최적화가 아니라, **사용할 필터 지표 자체를 바꾸는 요구사항 변경**이다. 위 수치는 관측 당시의 예시이며 고정 기대값으로 사용하지 않는다.

### 수정 방향

- 사용자의 요청에 따라 맞힌 사람 수(solver) 대신 **정답 제출 수**를 필터·정렬·출력 지표로 사용한다.
- 목록의 `td[data-col="정답"]`에서 정답 제출 수를 읽고, 난이도·정답률과 함께 목록 데이터만으로 필터링·정렬·추천한다. 정답률은 목록 표시값을 그대로 사용한다.
- 일반 조회·추천 과정에서 문제 상세 페이지 탐색과 상세 통계 보강 단계를 제거한다. 명시적인 `open` 명령으로 선택한 문제를 여는 기능은 유지한다.
- 기존 `--min-solvers`·`--max-solvers`·`--sort solvers`, 모델 필드와 출력 제목을 새 지표에 맞게 정리한다. 정답 제출 수를 맞힌 사람 수로 표시하거나 지표 변경을 설명 없이 적용하지 않는다.
- 난이도는 기존 `minTier`·`maxTier`·`unrated` URL 조건을 유지하고, 지정 공개 사용자의 풀이 조건은 기존 `solvedBy`·`solvedByMode`를 유지한다. 로그인 사용자용 `status=unsolved`로 바꾸지 않는다. 정답 제출 수와 정답률 범위는 수집한 목록에서 적용한다.
- 전체 후보 수집 후 필터·정렬·추첨하는 원칙은 유지한다. 시간 제한으로 일부 후보만 반환하는 기능이나 로컬 캐시는 이번 변경에 포함하지 않는다.
- 구현할 때 `spec.md`·`plan.md`·데이터 모델·계약·사용법·테스트를 새 지표와 목록 전용 처리 흐름에 맞춘다.

### 완료 조건

- 조회·추천이 목록의 정답 제출 수를 사용하고, 상세 페이지 탐색 없이 완료된다.
- 정답 제출 수의 최소·최대 경계를 포함한 필터와 양방향 정렬이 동작한다.
- 실제 0과 명시적인 미제공 값을 구분하고, 구조 변경·파싱 실패를 정상 값으로 바꾸지 않는다.
- 출력과 도움말에서 정답 제출 수와 맞힌 사람 수를 혼동하지 않는다.
- 전체 후보 기준 필터·정렬·중복 없는 추천, 후보 부족 안내 및 실패·취소 처리는 유지된다.
- 최소 회귀 검증으로 목록의 ‘정답’·‘시도’·‘정답률’을 구분하고, 조회·추천 중 상세 페이지 요청이 0건임을 확인한다.
- 같은 조건의 변경 전후 소요 시간을 비교해 상세 조회 제거 효과를 기록하되, 전체 목록 수집에 드는 시간은 별도로 남긴다.

## IDEA-001: 번호 오름차순 목록 조회의 조기 종료

- **상태**: 검토 아이디어, 미구현
- **우선순위**: 낮음
- **기록일**: 2026-10-20

### 현재 동작

`list --sort id --order asc --limit 10`도 전체 후보 수집과 조건 검사를 마친 뒤 10개를 출력한다. URL의 `sort=idAsc`를 이용해 필요한 개수만 확보하고 종료하는 최적화는 아직 없다.

### 가능한 최적화

- 정올의 목록이 페이지 전체에 걸쳐 번호 오름차순을 유지한다는 전제에서, 목록을 가져오는 대로 모든 필터를 적용하고 중복을 제거한다.
- 예를 들어 첫 50개에서 조건을 만족하는 고유 문제 10개를 확보하면 추가 수집을 종료하고 출력한다. 부족하면 다음 묶음을 확인한다.
- 필요한 지표까지 확인한 문제만 개수에 포함한다. ISSUE-002의 상세 조회 제거가 적용되면 목록 정보만으로 처리한다.

### 적용 조건과 제약

- 번호 오름차순 `list`에 한정해 검토한다. 전체 후보에서 균등하게 선택해야 하는 `recommend`나 `list --sort random`에는 적용하지 않는다.
- 조기 종료 시 전체 적격 개수는 알 수 없으므로 미확인으로 표시하고, 전체 목록을 수집했다고 안내하지 않는다. 사이트 목록이 끝났는데 요청 개수보다 적으면 확보한 문제만 출력한다.
- ISSUE-002에서 유지하기로 한 전체 후보 수집 원칙과 별개인 후속 최적화다. 실제 도입 시 명세·완료 판정·개수 출력 계약을 함께 조정하고, 전체 수집 결과의 앞부분과 동일한지 검증한다.

이 문서는 기존 수정 기록과 후속 이슈·합의한 변경 방향·검토 아이디어를 관리한다. ISSUE-001·ISSUE-002와 IDEA-001에 대한 코드 구현 및 기존 명세·계획·작업 목록 변경은 아직 수행하지 않는다.
