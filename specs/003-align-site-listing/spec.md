# Feature Specification: 사이트 목록 기준의 티어·빈 통계·수집 종료 정책

**Feature Branch**: `003-align-site-listing`

**Created**: 2026-10-22

**Status**: Draft

**Input**: [002 구현 이후 테스트 이슈](../002-improve-list-collection/post-implementation-issues.md)의 ISSUE-001·ISSUE-002와 2026-10-22 정책 변경 합의를 반영한다. ISSUE-003은 이번 수정 대상에서 제외한다.

사용자는 정올의 검색 조건으로 제공된 문제 목록을 조회하거나 추천받는다.  
표시 티어가 요청 범위와 다르더라도 사이트가 제공한 문제를 보존하고, 명시적인 빈 통계는 미제공으로 처리한다.  
더 불러오기 방식에서는 버튼이 없을 때 현재 목록을 읽어 수집을 완료한다.  
이 기능은 아래에 명시한 기존 정책을 대체하며, 해당 동작을 기존 명세의 단순 구현 오류로 취급하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 사이트가 제공한 티어 검색 결과로 조회·추천하기 (Priority: P1)

사용자는 사이트에 전달한 티어 검색 조건의 결과를 그대로 활용한다.  
사이트 결과와 표시 티어가 어긋난 문제 한 건 때문에 조회가 실패하거나 해당 문제가 자동 제외되지 않는다.

**Why this priority**: 실제 티어 9~13 목록에 표시 티어 8인 문제가 포함돼 전체 조회가 중단됐다.  
사용자가 사이트에서 문제를 고르는 수고를 줄이려는 도구의 목적에 맞춰 사이트 검색 결과를 따른다.

**Independent Test**: 정상적으로 읽을 수 있는 범위 안·밖 문제를 첫 목록·다음 페이지·추가 목록에 제공하고,  
티어 양쪽 경계·하한만·상한만 지정한 조회와 추천에서 문제 보존, 실제 티어 표시 및 다른 조건 적용을 확인한다.

**Acceptance Scenarios**:

1. **Given** 티어 9~13으로 검색한 사이트 목록에 표시 티어 8인 문제가 있고,  
   **When** 조회하거나 추천하면,  
   **Then** 해당 문제를 수집하고 티어 범위 차이만으로 실패·제외·추가 경고하지 않으며 표시 티어 8을 유지한다.
2. **Given** 하한만 또는 상한만 지정한 사이트 목록의 확정 티어가 모두 요청 범위 밖이고,  
   **When** 다른 활성 조건을 만족하는 문제를 조회하거나 추천하면,  
   **Then** 해당 문제도 적격 후보에 포함되며 범위 차이 때문에 후보 0개로 처리하지 않는다.
3. **Given** 범위 밖 티어 문제가 정답률 또는 정답 제출 수 조건을 만족하지 않고,  
   **When** 전체 수집 후 조건을 적용하면,  
   **Then** 해당 수치 조건에 따라 제외하며 티어 불일치와 혼동하지 않는다.
4. **Given** 검색 도중 요청한 티어 조건이나 지정 사용자의 풀이 조건이 손실되고,  
   **When** 후속 목록을 확인하면,  
   **Then** 조건 손실을 조회 실패로 알리고 최종 결과를 제공하지 않는다.
5. **Given** 정상적인 미정·미확인 티어 문제 또는 해석할 수 없는 티어 표시가 있고,  
   **When** 조회하면,  
   **Then** 정상적인 미정·미확인에는 기존 포함·제외 정책을 적용하고 표시 구조나 값의 오류는 실패로 알린다.
6. **Given** 사용자가 결과와 사용 안내를 확인하고,  
   **When** 요청한 티어 범위와 표시 티어를 비교하면,  
   **Then** 요청 조건과 관측한 표시값을 그대로 확인할 수 있고 티어 조건은 사이트 검색 조건이라는 의미를 이해할 수 있다.

### User Story 2 - 통계가 미제공인 문제가 있어도 조회·추천하기 (Priority: P1)

사용자는 정답 제출 수나 정답률을 제공하지 않는 문제가 섞여 있어도 다른 문제를 조회하거나 추천받는다.  
미제공 통계와 실제 숫자 0을 구분하고, 자신이 지정한 수치 조건에 맞는 결과를 받는다.

**Why this priority**: 실제 목록의 명시적인 빈 통계 한 건을 준비되지 않은 값으로 취급해,  
이미 추가된 문제들까지 처리하지 못하고 시간 초과로 종료됐다.

**Independent Test**: 첫 목록과 추가 목록에 실제 0, 정상 수치, 명시적인 미제공을 섞고,  
해당 지표의 필터 유무에 따른 수집·제외·표시와 모든 후보가 제외되는 정상 완료를 확인한다.

**Acceptance Scenarios**:

1. **Given** 사이트가 정답 제출 수 또는 정답률을 명시적인 빈 통계로 표시하고 해당 지표에 필터가 없으며,  
   **When** 첫 목록이나 추가 목록을 읽으면,  
   **Then** 수집을 계속하고 다른 조건을 만족하는 문제를 포함하며 해당 지표는 ‘미확인’으로 표시한다.
2. **Given** 명시적인 미제공 통계에 최소 또는 최대 조건이 지정됐고,  
   **When** 전체 수집 후 필터링하면,  
   **Then** 그 문제를 제외하며 여러 미제공 지표 때문에 같은 문제를 중복 집계하지 않는다.
3. **Given** 수집한 모든 문제가 활성 수치 조건의 미제공 지표 때문에 제외되고,  
   **When** 조회하거나 추천하면,  
   **Then** 적격 후보 0개로 정상 완료하고 조회의 결과 없음 또는 추천의 부족 안내를 제공한다.
4. **Given** 실제 통계 0인 문제와 미제공 문제가 함께 있고,  
   **When** 해당 지표의 범위를 0~0으로 지정하면,  
   **Then** 실제 0인 문제만 해당 조건을 통과하고 미제공을 0으로 바꾸지 않는다.
5. **Given** 명시적인 미제공 표시 없이 통계가 일시적으로 비어 있고,  
   **When** 이후 정상 통계가 표시되면,  
   **Then** 준비된 값을 읽고 임시 빈 값을 미제공으로 확정하지 않는다.
6. **Given** 통계 셀이 누락·중복되거나 숫자 표현을 해석할 수 없고,  
   **When** 목록을 읽으면,  
   **Then** 문제와 지표를 식별할 수 있는 실패를 알리고 이를 미제공이나 정상적인 빈 결과로 바꾸지 않는다.

### User Story 3 - 더 불러오기 버튼 상태에 따라 수집 완료하기 (Priority: P1)

사용자는 더 불러오기 버튼이 있는 동안 추가 목록을 수집하고, 버튼이 없으면 현재 목록으로 결과를 받는다.  
실사이트에서 확인되지 않은 지연 반영 가능성 때문에 별도의 완료 알림을 기다리다가 실패하지 않는다.

**Why this priority**: 실제 사이트는 마지막 추가 로드 후 버튼을 제거했으나,  
기존 프로그램은 별도의 목록 영역 완료 알림을 요구해 정상적인 목록을 완료하지 못했다.

**Independent Test**: 버튼 유지·제거, 새 행이 없는 최종 로드, 명시적인 빈 목록과 진행 없음 사례를 제공해,  
버튼 부재 시 현재 목록을 읽는 정상 완료와 실제 실패·취소를 구분한다.

**Acceptance Scenarios**:

1. **Given** 최초 목록이 정상적으로 표시됐고 더 불러오기 버튼이 없으며,  
   **When** 목록을 수집하면,  
   **Then** 현재 목록을 읽어 완료하고 별도의 목록 영역 로딩 종료 알림을 요구하지 않는다.
2. **Given** 추가 목록 반영 후 더 불러오기 버튼이 남아 있고,  
   **When** 조회나 추천에 필요한 표시 개수를 이미 확보했더라도,  
   **Then** 다음 목록을 계속 수집하고 버튼이 있는 동안 표시 개수만으로 조기 종료하지 않는다.
3. **Given** 추가 목록에 새 문제가 나타나고 더 불러오기 버튼이 없어졌으며,  
   **When** 현재 목록을 읽으면,  
   **Then** 그 목록의 고유 문제를 반영해 수집을 완료한다.
4. **Given** 최종 추가 로드에 새 문제가 없고 버튼이 없어졌거나, 사이트가 정상적인 빈 검색 결과를 표시하며,  
   **When** 현재 목록을 읽으면,  
   **Then** 별도 완료 알림 없이 현재 후보 또는 후보 0개로 정상 완료한다.
5. **Given** 합성 사례에서 버튼 제거 후 나중에 행이나 다음 버튼이 추가되며,  
   **When** 버튼이 없는 시점의 현재 목록을 읽으면,  
   **Then** 현재 목록으로 완료할 수 있으며 나중에 나타날 결과를 반드시 기다리거나 포함할 것을 요구하지 않는다.
6. **Given** 더 불러오기 버튼이 남아 있으나 추가 수집이 진행되지 않고 기존 제한 시간에 도달하며,  
   **When** 조회가 종료되면,  
   **Then** 진행 실패를 알리고 현재 후보로 만든 최종 결과를 제공하지 않는다.
7. **Given** 수집 중 접근 오류·구조 오류가 발생하거나 사용자가 취소하고,  
   **When** 실행이 종료되면,  
   **Then** 실패 또는 취소를 구분해 알리고 해당 실행의 최종 표나 추천 결과를 제공하지 않는다.

### Edge Cases

- 범위 밖 확정 티어가 최초·번호 페이지·추가 목록 어디에 있어도 같은 보존 정책을 적용한다.  
  유효한 티어 값의 범위 검증과 사용자가 요청한 검색 범위의 비교는 구분한다.
- 티어 범위가 있을 때 정상적인 미정·미확인은 기존대로 제외한다. 티어 범위가 없으면 포함하고,  
  난이도 양방향 정렬에서 마지막에 두는 기존 동작을 유지한다.
- 명시적인 미제공은 정답률과 정답 제출 수 각각에 적용한다. 두 지표가 모두 미제공이어도  
  필터 때문에 제외한 고유 문제 수는 한 번만 센다.
- 명시적 미제공 표시가 없는 임시 빈 통계, 통계 구조 손실과 잘못된 숫자는 명시적인 미제공과 구분한다.
- 더 불러오기 버튼이 로딩 중이거나 일시적으로 조작 불가능해도 버튼이 존재하는 상태를 목록 종료로 보지 않는다.
- 버튼이 없을 때 현재 목록의 유효한 문제 또는 명시적인 빈 결과를 읽어 완료한다.  
  접근 제한이나 깨진 목록을 버튼 부재만으로 정상 완료시키지 않는다.
- 버튼 제거 후 늦게 나타나는 문제를 모두 포함한다는 보장은 두지 않는다.  
  이후 실사이트에서 같은 순서가 관측되면 재현 근거로 종료 정책을 재검토한다.
- 여러 목록에 같은 번호가 반복되면 고유 문제 한 건으로 세고 최초 관측 정보를 유지한다.
- 실패·취소 시 표시하는 누적 수집 개수는 이번 수용 기준에 포함하지 않는다.  
  실패·취소한 실행의 최종 결과 미제공은 계속 수용 기준이다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 요청한 티어 하한·상한·미정 포함 정책과 지정 공개 사용자의 풀이 조건을 사이트에 전달하고,  
  최초·후속 목록에서 요청 조건이 유지되는지 확인해야 한다. 조건 손실은 실패로 처리해야 한다.
- **FR-002**: 사이트가 제공한 정상적인 범위 밖 확정 티어 문제는 최초·번호 페이지·추가 목록에서 모두 수집해야 한다.  
  표시 티어와 요청 범위의 차이만으로 실패하거나 문제를 제외하거나 추가 경고해서는 안 된다.
- **FR-003**: 전체 수집 후에도 확정 티어를 요청 범위와 다시 비교해 제외해서는 안 된다.  
  양쪽 경계·한쪽 경계 모두에 적용하며 다른 활성 조건을 만족하면 적격 후보와 추천 대상에 포함해야 한다.
- **FR-004**: 표시 티어를 요청 범위에 맞춰 바꾸지 않고 실제 관측값을 결과에 보존해야 한다.  
  정상적인 미정·미확인 티어의 기존 포함·제외·정렬 정책과 잘못된 티어 표시의 실패 처리는 유지해야 한다.
- **FR-005**: 사이트가 명시한 빈 정답 제출 수·정답률을 정상적인 미제공 상태로 인정하고 수집을 계속해야 한다.  
  목록 준비 판정부터 결과 처리까지 같은 의미를 적용하고 실제 숫자 0과 구분해야 한다.
- **FR-006**: 미제공 지표에 필터가 있으면 해당 문제를 제외하고, 필터가 없으면 다른 조건을 만족하는 문제를  
  포함할 수 있어야 하며 해당 지표를 ‘미확인’으로 표시해야 한다. 미확인 지표의 정렬 위치는 기존대로 유지해야 한다.
- **FR-007**: 필터링 결과가 0개여도 정상 완료해야 한다. 적격 개수와 미확인 지표로 제외한 개수는 고유 문제 기준으로  
  계산하고 조회의 결과 없음, 추천의 요청 개수·반환 개수·부족 안내를 실제 결과에 맞춰 제공해야 한다.
- **FR-008**: 명시적인 미제공과 임시 빈 통계·구조 누락·중복·해석 실패를 구분해야 한다.  
  준비되지 않은 값은 기존 준비 판정에 따라 기다리되 준비 실패나 구조·파싱 오류를 미제공이나 0으로 대체해서는 안 된다.
- **FR-009**: 더 불러오기 방식에서 버튼이 있으면 계속 수집하고, 없으면 현재 목록의 문제 또는 명시적인 빈 결과를  
  읽어 수집 완료로 처리해야 한다. 새 행이 없는 최종 로드에도 동일한 기준을 적용해야 한다.
- **FR-010**: 더 불러오기 버튼이 없는 경우 별도의 목록 영역 로딩 종료 알림을 필수로 요구해서는 안 된다.  
  알림이 없다는 이유만으로 추가 대기나 실패를 강제하거나, 이후에 나타날 행·버튼까지 반드시 기다리게 해서는 안 된다.
- **FR-011**: 더 불러오기 종료 정책을 번호 페이지 이동이나 지정 사용자 검색의 완료 판정 변경으로 확대해서는 안 된다.  
  버튼이 남아 있으나 진행이 없는 경우와 접근·구조·파싱 실패는 기존 오류 처리와 제한을 유지해야 한다.
- **FR-012**: 수집 종료 기준까지 확인한 모든 고유 후보에 대해 기존 로컬 수치 필터·정렬·중복 없는 무작위 추천을  
  수행해야 한다. 표시·추천 개수가 작다는 이유로 수집을 일찍 끝내거나 문제를 중복 집계해서는 안 된다.
- **FR-013**: 실패·취소 상태를 알리고 해당 실행의 최종 표나 추천 결과를 제공하지 않아야 한다.  
  실패·취소 시 누적 수집 개수 보존이나 진행 정보 전달 방식 개선은 이번 요구사항이나 선행 조건으로 두지 않는다.
- **FR-014**: 사용 안내는 티어 옵션이 사이트 검색 조건이며 표시 티어의 범위 일치를 보장하지 않는다는 점,  
  명시적인 빈 통계의 미제공 처리와 더 불러오기 종료 기준을 결과의 의미와 일치하게 설명해야 한다.
- **FR-015**: 변경된 정책에 맞춰 관련 검증의 기대 동작을 갱신하고, 합성 사례와 실사이트 관측을 구분해 기록해야 한다.  
  기존의 지연 반영 합성 사례를 실사이트에서 발생한 사실로 설명하거나, 정책을 대체한 과거 검증 결과를 새 정책의 검증으로 간주해서는 안 된다.

### Key Entities *(include if feature involves data)*

- **검색 조건**: 사이트에 전달하는 티어 범위·미정 포함 정책·지정 사용자 풀이 조건과,  
  수집 후 적용하는 정답률·정답 제출 수 조건을 포함한다. 티어 조건의 의미는 사이트 검색 결과의 선택이다.
- **문제 관측 정보**: 번호·제목·링크·실제 표시 티어·정답률·정답 제출 수·관측 시점으로 구성한다.  
  통계는 실제 0을 포함한 제공 수치와 미제공을 구분하고 같은 번호의 최초 관측값을 유지한다.
- **목록 수집 결과**: 사이트가 제공한 목록에서 종료 기준까지 확인한 고유 문제 집합이다.  
  사이트의 누락이나 버튼 부재 판정 뒤의 지연 반영까지 복구했다는 의미는 아니다.
- **조회·추천 결과**: 검색 조건, 수집·적격·반환 개수, 미확인 지표로 제외한 개수와 실제 표시값을 포함한다.  
  실패·취소한 실행에서는 생성·제공하지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 최초·번호 페이지·추가 목록 및 티어 양쪽·한쪽 경계의 모든 검증 사례에서,  
  정상적인 범위 밖 확정 티어 때문에 발생하는 실패·자동 제외·추가 경고는 0건이며 표시 티어 보존율은 100%다.
- **SC-002**: 정답 제출 수·정답률 각각에 대해 실제 0·정상 수치·명시적 미제공·임시 빈 값·구조 오류를 구분하는  
  검증 결과가 기대값과 100% 일치하고, 명시적 미제공 한 건 때문에 전체 수집이 중단되는 사례는 0건이다.
- **SC-003**: 미제공 지표의 필터 유무, 0~0 조건, 모든 후보 제외 및 복수 미제공 검증에서,  
  포함·제외·미확인 표시·고유 제외 수와 정상 0개·추천 부족 안내가 기대값과 100% 일치한다.
- **SC-004**: 버튼 유지·제거·새 행 없는 최종 로드·정상 빈 결과 사례에서,  
  버튼이 있으면 추가 수집하고 없으면 현재 목록으로 완료하는 동작의 일치율은 100%다.  
  버튼이 없는 정상 목록에서 별도 목록 영역 완료 알림 부재 때문에 발생하는 실패는 0건이다.
- **SC-005**: 정책에 맞춘 합성 사례에서 버튼 부재 시 읽은 현재 후보 집합과 조회·추천 대상 집합이 다른 로컬 조건을  
  고려한 기대값과 100% 일치한다. 미래 지연 반영을 반드시 포함해야 한다는 기대를 수용 기준으로 남기지 않는다.
- **SC-006**: 여러 목록·중복 번호·표시 또는 추천 1개 사례에서 수집·적격·반환 개수와 정렬 결과가 기대값과  
  100% 일치하며 중복 반환은 0건이다. 실패·취소 사례의 최종 결과 제공은 0건이다.
- **SC-007**: 원문에 기록한 티어 9~13 추천, 티어 9~10 추천, 티어 1의 정답 제출 수 내림차순 조회를  
  실사이트에서 각각 검증하고, 사이트가 정상 접근 가능한 경우 세 명령 모두 새 정책에 따라 결과 또는 정상적인 결과 없음을 제공한다.  
  실행 조건·관측 시점·성공/실패·미실행 여부를 기록하며 과거 관측 개수를 고정 기대값으로 사용하지 않는다.
- **SC-008**: 사용자는 갱신된 안내만으로 티어 검색 결과의 의미, 미확인 통계의 필터 처리,  
  더 불러오기 종료 기준을 확인하고 기존 조회·추천 명령을 코드 수정 없이 실행할 수 있다.  
  안내와 실제 결과의 정책 설명 사이에 상충하는 항목은 0개다.

## Assumptions

- 범위는 원문 ISSUE-001·ISSUE-002다. ISSUE-003의 실패·취소 시 누적 개수 보존과 진행 정보 전달 방식 변경은 제외한다.  
  기존 기본 정렬·표시·추천 개수, 공개 사용자 기준, 선택한 문제 열기와 실패·취소 구분은 유지한다.
- 사이트가 제공한 티어 검색 결과를 따르며 사이트 내부의 필터·표시 데이터 불일치 원인은 확정하지 않는다.  
  누락된 문제를 찾아 전체 문제은행을 다시 수집하거나 문제별 상세 조회로 보강하지 않는다.
- 명시적인 빈 통계는 원문의 실사이트 관측을 근거로 인정한다. 새 표현이나 임의의 빈 문자열까지  
  정상 미제공이라고 가정하지 않는다. 구체적인 표현의 식별 기준은 이 정책을 보존해 후속 계획에서 정한다.
- 더 불러오기 버튼 부재는 이번 합의에서 채택한 종료 기준이다. 실사이트에서 버튼 제거 후 지연 반영이 없다고  
  증명한 것은 아니며, 이후 재현이 확인되면 그 근거로 보완한다. 추가 완료 신호 탐색을 이번 작업의 선행 조건으로 두지 않는다.
- 실사이트 수용은 원문 세 명령을 기준으로 하며 2026-10-21의 550·200·100개 로그와 250·134개 관측은 재현 설명이다.  
  변화하는 문제 수·통계·사이트 상태를 고정 정답이나 성능 보장으로 삼지 않는다.
- 기존에 합의한 공개 목록 기반 접근과 목록 전용 처리를 유지한다. 새 데이터 접근 방식, 영구 캐시,  
  오프라인 조회·다른 플랫폼 지원은 추가하지 않는다. 영구 캐시 제외는 기존 사용자 합의 범위를 유지하는 것으로,  
  헌장 III의 영구 캐시 원칙과의 차이는 후속 계획의 정합성 검토에 기록한다.
- 이번 단계에서는 003 명세·품질 체크리스트·활성 기능 경로를 작성한다.  
  제품 코드·사용 안내·테스트·계획·작업 목록의 실제 변경과 실행 검증은 후속 단계에서 수행한다.
