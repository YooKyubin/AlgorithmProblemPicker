# 002 구현 이후 테스트 이슈

실사용 테스트에서 발견한 문제, 원인 조사 결과와 후속 수정 방향을 기록한다.
실사이트 확인일은 2026-10-21이며, 수집 개수와 화면 값은 당시 관측값이다.
ISSUE-002의 정책 변경과 ISSUE-003의 수정 범위 제외는 2026-10-22 합의했다.
이 문서는 구현 작업 목록과 별도로 관리한다.

## ISSUE-001: 범위 밖 티어 한 건으로 전체 수집 중단

- **상태**: 수정 방향 합의, 미구현
- **확인일**: 2026-10-21

### 발생 내용과 재현

```powershell
uv run --locked jpick recommend --min-tier 9 --max-tier 13 --count 2
```

```text
Collecting · 수집 550개 · Ctrl+C 취소
Failed · 수집 0 · Ctrl+C 취소
조회 실패: 문제 8213: 확정 티어 8, 요청 범위 하한 9, 상한 13; 목록 티어 필터 미적용
```

[재현 목록 URL](https://jungol.co.kr/problem?type=problem&sort=idAsc&unrated=exclude&minTier=9&maxTier=13)에서
‘더 불러오기’를 반복해 총 600개를 표시하면, 550개 이후의 묶음에
[8213번 ‘루트에서 리프까지’](https://jungol.co.kr/problem/8213)가 나타났다.
최초 50개 기준으로 추가 로드 11회이며 URL은 그대로 유지됐다.
사용자도 같은 목록에서 해당 문제와 배지를 직접 확인했다.

### 확인된 원인과 조사 한계

- 요청 URL과 공개 필터 UI는 티어 9~13을 유지했다.
- 8213번 문제 행의 실제 배지는 `/solved/8.svg`였다. 프로그램의 티어 숫자 파싱 오류는 아니다.
- 사이트의 필터 결과와 표시 티어가 불일치하는 사례다. 사이트 내부의 필터·표시 데이터 중
  어느 쪽이 어긋났는지는 확정하지 않았다.
- 티어 변경의 반영 지연으로 유사 사례가 반복될 수 있다는 것은 사용자가 제시한 가능성이다.
  실제 갱신 주기나 캐시 구조를 확인한 것은 아니다.
- `jungol.py`의 `_collect`는 정상적으로 읽은 확정 티어가 요청 범위를 벗어나면
  `SourceAccessError`를 발생시킨다. 이 정책 때문에 한 건의 불일치가 전체 조회·추천을 막는다.
- `selection.py`의 `filter_listing`은 이미 전체 수집 후 티어 범위를 검사한다.
  따라서 수집 단계의 범위 이탈 예외와 최종 후보 필터가 중복돼 있다.

### 합의한 수정 방향

- 이 도구는 사용자가 사이트에서 필터를 선택하고 문제를 고르는 수고를 줄이는 것이 목적이다.
  티어 필터의 결과는 사이트가 제공한 목록을 따르며, 표시 티어로 사이트의 결과를 다시 보정하지 않는다.
- 수집 중 요청 티어 범위를 벗어났다는 이유로 예외를 발생시키는 검사를 제거한다.
  정상적으로 파싱한 문제는 수집 레코드에 보존하고 다음 목록을 계속 확인한다.
- 전체 수집 후 `filter_listing`에서도 확정 티어를 요청 하한·상한과 다시 비교해 제외하지 않는다.
  위 사례의 8213번은 표시 티어 8을 그대로 보존하며, 다른 활성 조건을 만족하면
  티어 9~13 요청의 적격 후보나 추천 결과에도 포함될 수 있다.
- 정답률·정답 제출 수 등 사이트에 맡기지 않은 기존 로컬 필터는 유지한다.
  이번 합의는 확정 티어의 요청 범위 비교에 관한 것이며, 정상 미정·미확인 티어의 기존 처리 정책은 유지한다.
- `minTier`·`maxTier`·`unrated` 조건을 전달하고 URL·공개 필터 UI의 조건 손실을 확인하는 동작은 유지한다.
- 알 수 없는 배지·표시 구조 누락·중복·파싱 실패는 계속 오류로 처리한다.
  배지 값의 유효 범위 0~30 검증과 사용자가 요청한 티어 범위의 비교는 구분한다.
- 범위 밖 티어가 한 건 섞였다는 이유로 상세 조회를 추가하거나 전체 문제은행을 다시 수집하지 않는다.

### 테스트에서의 활용

- 회귀 테스트에는 범위 밖 확정 티어를 넣어 수집·결과 처리가 중단되지 않고,
  해당 문제를 티어만으로 제외하지 않는지 확인한다. 표시 티어를 요청 범위에 맞춰 바꾸지도 않는다.
- 요청 하한·상한·미정 제외 조건의 URL 전달과 공개 UI 확인, 배지 파싱은 별도로 검증한다.
- 표시 티어와 요청 범위의 일치 여부를 비교하는 진단이 필요하면 선택적인 라이브 검증 도구나
  테스트 내부에서만 활용한다. 불일치 관측은 제품의 실행 실패나 자동 제외로 연결하지 않는다.
- 사이트가 항상 범위 안 티어만 반환한다는 가정을 일반 회귀 테스트의 성공 조건으로 삼지 않는다.
  범위 비교를 테스트에서 사용하기 위해 제품에 별도 공개 API나 실행 옵션을 추가하지 않는다.

### 결과 의미와 제약

티어 옵션은 사이트에 전달하는 검색 조건을 의미한다.
최종 결과의 표시 티어가 요청 범위 안에 있다는 보장은 제공하지 않는다.
요청 조건과 실제 표시 티어는 그대로 출력하고, 사용 안내에도 사이트 필터 결과를 따른다는 의미를 반영한다.
사이트가 범위 안 문제를 반환하지 않는 경우에도 이 도구가 누락을 복구하지 않는다.
전체 후보 수집은 해당 사이트 목록에서 제공하는 전체 고유 후보를 확인한다는 의미이며,
사이트가 누락한 문제까지 확보했다고 주장하지 않는다.

### 완료 조건

- 첫 목록·다음 페이지·더 불러오기에서 정상적인 범위 밖 티어 때문에 전체 수집이 실패하지 않는다.
- 양쪽 경계·하한만·상한만 지정해도 확정 티어의 요청 범위 비교로 문제를 제외하지 않는다.
- 범위 밖 확정 티어 문제만 수집돼도 다른 활성 조건을 만족하면 적격 후보와 추천에 포함될 수 있다.
- 수집 고유 개수와 적격 개수는 실제 처리 결과를 반영하고 표시 티어는 관측값을 유지한다.
- 제품 실행 경로에는 확정 티어의 요청 범위 이탈을 이유로 한 실패·제외·추가 경고가 없다.
- 테스트에서 요청 조건 전달, 실제 배지 파싱, 범위 밖 문제의 보존과 다른 로컬 필터의 동작을 확인한다.
- 티어 구조·파싱 오류, 요청 조건 손실, 접근 실패와 실제 수집 미완료는 계속 실패로 구분한다.

## ISSUE-002: 추가 목록의 준비 또는 완료를 확인하지 못해 시간 초과

- **상태**: 수정 방향 합의, 미구현
- **확인일**: 2026-10-21
- **정책 변경 합의일**: 2026-10-22

### 발생 내용

```powershell
uv run jpick recommend --min-tier 9 --max-tier 10 --count 2
uv run --locked jpick list --min-tier 1 --max-tier 1 --sort accepted --order desc --limit 5
```

티어 9~10 추천은 사용자 실행 두 번 모두 수집 200개 이후 실패했고,
티어 1 조회는 수집 100개 이후 실패했다.

```text
조회 실패: 목록 준비 시간 초과 또는 추가 로드 진행 없음. DOM 구조와 접속 상태를 확인하세요.
```

실사이트 진단 결과는 다음과 같다. 두 경우 모두 실패 당시 진행 중인 관련 요청은 없었다.

| 조건 | 마지막 처리 완료 로그 | 실패 당시 실제 DOM | 다음 버튼 | 빈 통계 문제 |
| --- | --- | --- | --- | --- |
| 티어 9~10 | 200개 | 250개 | 있음 | 10872번 ‘압축’ |
| 티어 1 | 100개 | 134개 | 없음 | 10697번 ‘세계에서 가장 빠른 정렬 알고리즘’ |

즉, 로그에 찍힌 수 이후로도 실제 행은 추가됐다. 이 오류 문구만으로 네트워크 지연이나
추가 로드 진행 없음으로 판단할 수 없다.

### 원인 A: 명시적인 빈 정답 셀을 계속 로딩으로 판단

두 문제의 정답·정답률 셀에는 빈 앵커와 `data-col-empty`가 있었다.
10872번의 정답 셀 관측 형태는 다음과 같으며, 스타일 클래스는 생략했다.

```html
<td data-col="정답" data-col-empty>
  <a href="/problem/10872"></a>
</td>
```

- `_wait_listing`은 모든 행의 정답 셀 텍스트가 비어 있지 않아야 목록을 준비 완료로 인정한다.
  명시적인 빈 셀이 한 개라도 있으면 이 조건이 계속 거짓이 된다.
- `_problem`도 정답 제출 수의 빈 문자열을 정상적인 미제공 표현으로 지원하지 않는다.
  준비 판정만 바꾸면 이후 정답 파싱에서 다시 실패한다.
- 정답률 파서는 해당 문제를 가리키는 빈 링크를 이미 `Unavailable`로 처리한다.
  정답 제출 수에는 이 실사이트 표현의 지원이 빠져 있다.
- 빈 칸이 표시된 내부 이유나 공개 정책은 이번 조사로 확정하지 않았다.
  해당 표시는 수치 0을 의미하지 않는다.

### 원인 B: 마지막 묶음의 완료 관찰 대상이 실제 화면과 다름

- `_LIST_UPDATE`는 `article`·`table`·`tbody`의 `aria-busy`가 `true`에서 해제되는 변화만
  해당 로드의 완료 근거로 인정한다.
- 실제 관측에서는 ‘더 불러오기’ 버튼에 `aria-busy="true"`가 붙었다.
  티어 9~10에서는 버튼의 로딩 속성이 해제됐고, 티어 1의 마지막 로드에서는 버튼이 제거됐다.
- 티어 1은 134개 행이 있고 다음 컨트롤이 없었지만 관찰자의 `completed`는 `false`였다.
  따라서 원인 A를 수정해도 현재 완료 조건에서 다시 막힌다.
- 티어 9~10의 250개 시점에는 다음 버튼이 남아 있었다. 이 시점의 직접적인 진행 차단은 원인 A다.

### 합의한 수정 방향 A: 명시적인 빈 통계는 미제공으로 처리

- 사이트가 `data-col-empty` 등으로 명시한 빈 통계 셀을 정상적인 미제공 상태인 `Unavailable`로 인정한다.
  준비 판정과 통계 파서 모두에 반영하고 수집을 계속한다. 수치 0으로 채우지 않는다.
- 해당 지표에 필터가 있으면 그 문제를 제외하고, 필터가 없으면 ‘미확인’으로 표시한다.
  전체 수집 후 필터링 결과가 0개여도 정상 완료로 처리한다.
- 유효한 문제 행·해당 통계 셀·명시적인 빈 상태를 함께 확인한다.
  임시로 비어 있는 셀, 구조 누락·중복·파싱 오류까지 미제공으로 바꾸지 않는다.

**근거와 의도**: 실사이트에서 명시적인 빈 통계 표현을 확인했다. 통계를 제공하지 않는 문제 한 건 때문에
다른 문제의 조회·추천까지 막을 필요는 없다. 기존 002의 ‘빈 정답 셀은 오류’ 규칙을 실제 사이트 표현에 맞게 변경한다.

### 합의한 수정 방향 B: 더 불러오기 버튼의 부재를 종료 기준으로 사용

- 더 불러오기 방식의 목록에서 버튼이 있으면 계속 수집한다.
  버튼이 없으면 현재 목록을 읽어 수집 완료로 처리한다.
- 별도의 목록 영역 `article`·`table`·`tbody`의 `aria-busy` 종료 신호를 필수로 요구하지 않는다.
  버튼이 없다는 이유로 추가 완료 근거를 기다리다가 실패시키는 기존 판정을 변경한다.
- 이 결정은 더 불러오기 방식의 종료 기준에 관한 것이다.
  번호 페이지 이동과 사용자 검색의 완료 판정을 변경하는 요구사항으로 확대하지 않는다.
- 이후 실사이트에서 버튼 제거 후 행이나 다음 버튼이 지연 반영되는 순서가 실제로 관측되면,
  그 재현 근거를 바탕으로 완료 판정을 보완한다.

**근거와 의도**: 이번 실사이트 조사에서는 버튼이 사라진 뒤 뒤늦게 문제가 추가되는 순서를 확인하지 못했다.
해당 상황과 다음 버튼의 지연 반영은 합성 테스트로 구성한 사례였다. 이 순서가 실사이트에서 발생하지 않는다고
단정하는 것은 아니며, 이번에는 미관측 가능성을 막기 위한 복잡한 완료 조건보다 실제 조회의 정상 완료를 우선한다.

### 기존 합성 테스트와의 관계

- 001/T038·T041에서 버튼 부재만으로 종료하지 않도록 요구했던 테스트의 기대 동작을 이번 정책에 맞춘다.
  버튼 제거 후 지연된 행·다음 버튼까지 반드시 기다리거나, 별도 목록 영역의 완료 신호가 없으면
  반드시 실패해야 한다는 기존 기대는 더 불러오기 방식의 필수 조건으로 유지하지 않는다.
- 버튼이 없는 시점의 현재 목록을 읽어 완료하는 동작은 이번 정책에 따른 정상 완료다.
  이후 지연 반영될 가능성까지 모두 확인했다는 보장은 제공하지 않는다.
- 접근·구조·파싱 오류, 버튼이 남아 있으나 추가 로드가 진행되지 않는 경우 등 실제 실패와 취소 처리는 유지한다.
  실패·취소 시 해당 실행의 최종 표나 추천 결과를 제공하지 않는다.
- 합성 테스트와 실사이트 관측을 구분해 기록한다. 과거 합성 테스트를 실사이트에서 관측한 사실로 설명하지 않는다.

### 완료 조건

- 명시적 빈 통계가 있는 첫 목록·추가 목록에서도 수집이 진행되고, 값은 0과 구분된다.
- 빈 통계 표현을 지원한 뒤에도 실제 숫자·명시적 미제공·임시 빈 값·구조 오류를 구분한다.
- 미제공 지표의 필터 유무에 따른 제외·미확인 표시와 필터링 결과 0개의 정상 완료를 확인한다.
- 더 불러오기 버튼이 있으면 계속 수집하고, 버튼이 없으면 현재 목록을 읽어 완료한다.
  마지막 로드에 새 행이 없어도 버튼이 없으면 같은 종료 기준을 적용한다.
- 더 불러오기 방식에서 별도의 목록 영역 `aria-busy` 종료 근거가 없다는 이유로 실패하지 않는다.
- 관련 합성 테스트의 기대 동작을 새 정책에 맞추고, 진행 없음·접근 실패·구조 오류·취소는 별도로 검증한다.
- 실패·취소 상태를 알리고 해당 실행의 최종 표나 추천 결과를 제공하지 않는 동작을 유지한다.
- 합성 fixture의 성공과 실사이트 완료 검증을 구분해 기록한다.
  ISSUE-001도 해결한 뒤 위 두 명령의 전체 수집·필터·정렬 또는 추천 완료를 확인한다.

## ISSUE-003: 실패 시 누적 수집 개수가 0으로 표시됨

- **상태**: 원인 확인, 이번 수정 대상에서 제외
- **확인일**: 2026-10-21
- **범위 제외 합의일**: 2026-10-22

### 발생 내용과 원인

수집 550개·200개·100개 로그 이후 모두 `Failed · 수집 0`이 표시됐다.

- `JungolSource`는 자체 `candidates` 개수를 문자열로 직접 보고한다.
- `Picker`는 별도 `Progress`를 사용하며 `collected`의 초기값은 0이다.
- 서비스의 개수는 `source.collect`가 성공적으로 반환된 뒤에만 갱신된다.
  수집 중 예외가 발생하면 초기값 0인 상태로 `Failed`를 보고한다.
- CLI는 수집기의 문자열 보고와 서비스의 `Progress` 보고를 각각 출력한다.
  두 경로가 수집 진행 정보를 공유하지 않아 서로 다른 개수가 나타난다.

관련 위치는 `jungol.py`의 `_collect`, `service.py`의 `Picker._run`,
`cli.py`의 `_run`·`_progress`, `models.py`의 `Progress`다.

### 이번 결정

- 기존 문서에 실패·취소 시 수집 개수를 0으로 표시하라는 요구사항은 없다. 현재 표시는 기존 진행 표시 의도와
  어긋나는 구현 문제로 기록하며, 의도한 정책이었다고 해석하지 않는다.
- 다만 사용자는 실패·취소 시 누적 수집 개수 표시를 중요한 요구사항으로 두지 않으므로 이번 수정 대상에서 제외한다.
- 앞서 제안한 진행 정보 전달 방식 변경, 누적 개수 보존 및 관련 완료 조건은 이번 요구사항에 포함하지 않는다.
  ISSUE-001·ISSUE-002의 완료나 구현을 막는 선행 조건으로도 두지 않는다.
- 실패·취소 상태를 알리고 해당 실행의 최종 표나 추천 결과를 제공하지 않는 동작은 유지한다.
